# packages/db

- Files Node runs directly (`migrate.ts`, `cli/*` and what they import statically) keep `.ts` import extensions; files the app bundles don't, even when a CLI loads them too (`src/schema/`, `@repo/households`' `seed.ts` and `world.ts`).
- `src/schema/` is bundler-style, so a Node entry that needs it calls `registerTsResolution()` (`src/cli/ts-resolution.ts`) and then `await import()`s it.
- Better Auth's tables (`schema/auth.ts`, `schema/organization.ts`) keep Better Auth's names. Tables Cognitive Wealth owns use `GLOSSARY.md`'s, so a domain table's Firm column is `firm_id`, referencing `organization.id`.
- Follow the `drizzle` skill: tables in `src/schema/` (one file per family, `_helpers.ts` ids and timestamps, `_domain.ts` the `firm_id` column, its `firmIsolation()` policy and the enum checks of Cognitive Wealth's own tables), no serial/composite PKs, `db.select()` builders only (no `db.query`).
- Migrations live in `migrations/` and run as the `migrator` role; the app connects as `app` (DML only), both created by `docker/initdb/01-roles.sh`.
- A branch keeps one migration per change, so a later schema edit regenerates the branch's own unmerged one rather than adding a second (#199): delete its `migrations/<n>_<name>.sql` and `migrations/meta/<n>_snapshot.json`, restore the journal with `git checkout origin/dev -- packages/db/migrations/meta/_journal.json`, then `pnpm --filter @repo/db db:generate --name <name>`. Deleting only the SQL leaves the snapshot, and the next generate sees no change. Statements written by hand into the migration (grants, policies, `revoke`s) aren't regenerated: copy them out first and back after. `drizzle-kit drop` does the first two steps but only interactively, which the Bash tool can't answer.
- In a `` sql`…` `` template, an interpolated JS array becomes a list of parameters (`$1, $2, …`), not one array parameter, so `unnest(${names}::text[])` fails. Build a Postgres array with `sql.join` (`textArray` in `app-never-rules.integration.test.ts`; move it into `src/` once a second caller needs it). A backtick anywhere inside the template, an SQL comment included, ends it, and Vitest reports only a parse error (#205).
- Where each database's privileges come from (#202): `01-roles.sh` runs once, when a server's data folder is first created, and sets up only `POSTGRES_DB` (`cognitive_wealth`; Testcontainers' `test_base`, e2e's `e2e_template`): the schema grant and `migrator`'s default privileges (`usage, select on sequences` to `app`). Those belong to that one database, so every other one gets them by being cloned from it: the Testcontainers package templates, `wt_*` worktree databases (`packages/dev-env/src/setup.ts`), `verify_*` databases (`verifier-web`'s `start-app.sh`) and e2e's per-worker copies. Database-level grants (`connect`) aren't copied by a clone, so each of those repeats them. Editing `01-roles.sh` therefore changes nothing on a server that already exists: a change to a default privilege also needs a migration that makes it (as `0008_app_privileges` revoked `app`'s table defaults).
- `app` has no default privileges on tables (migration `0008_app_privileges`, #190): the migration that creates a table grants `app` exactly what code uses today, down to the columns an `update` may change, and adds the table to `APP_PRIVILEGES` (`src/app-privileges.ts`). `app-privileges.integration.test.ts` fails until the two agree. A later feature that needs more grants it in its own migration, except what `app-never-rules.integration.test.ts` forbids from names it writes out itself, so a change to the list and the migration together still fails it (#203): `update`, `delete` or `truncate` on a fact (the Custodian feed, `audit_event`), `delete` on `custodial_account` or `security`, `truncate` on any table, and `update` on any `firm_id`, on `id` and `public_id` outside Better Auth's tables (`BETTER_AUTH_TABLES`, read from their Drizzle tables; `@repo/auth`'s `auth.integration.test.ts` checks it against what Better Auth's config needs), or on a natural key (`custodial_account.account_number`, `security.identifier`, `custodial_transaction.transaction_id`). Loosening one is a rule change: edit that test, and say why in the PR. The same test fails until a new table is in exactly one of its groups (`FACTS`, `CUSTODIAN_RECORDS`, `MAY_CHANGE`; Better Auth's are found on their own), so deciding whether it holds facts is part of creating it.
- A Firm-scoped table (one with `firmId()`) also gets `firmIsolation()` in its extra config: row-level security that holds `app` to the transaction's Firm (ADR 0020). `firm-isolation.integration.test.ts` fails until it has both. Every exported domain function that touches one runs its queries in `withFirm(db, { firmId, query })` (`src/firm.ts`), from the Firm it was given, and keeps its `where firm_id = …` filters; outside `withFirm` they fail with `Firm not set`. Tests set up and inspect those rows as `migratorOrm`, the tables' owner, which the policies don't hold, and run the code under test as `orm` (`app`).
