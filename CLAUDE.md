# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

@AGENTS.md

## Overview

pnpm + Turborepo monorepo, scaffolded from `create-turbo`. Toolchain is pinned to recent majors: Node >=24, pnpm 12, TypeScript 7, Next.js 16, React 19, Oxlint + Oxfmt (no ESLint/Prettier). Don't assume older-version APIs or config formats.

Every package targets ES2025 (`lib` and `target` in `packages/typescript-config/base.json`, `env` in `.oxlintrc.json`), and `apps/web`'s `browserslist` names current Chrome only (`chrome >= 153`), so `Map.groupBy`, `toSorted`, the Set methods and iterator helpers are fine on both server and client, with no polyfill. That's deliberate, not an oversight: this is a learning project that never launches, its one User runs the latest Chrome, and e2e runs Playwright's Chromium. Don't lower either to support another browser without an issue that decides it (#116).

The browserslist query is a floor, not `last 2 Chrome versions`: Turbopack has its own browser data (Chrome up to 153 in Next 16.4.2), and a version it doesn't know yet silently compiles all client JS down to ES5, 38% bigger. A new floor must be one Next's Turbopack knows, so check client JS size before and after raising it.

What the product is, its principles, the synthetic world it runs on and the phase plan: [docs/product.md](docs/product.md). Read it before planning a feature; each phase has a GitHub issue.

## Worktrees

Every task that changes the repo runs in its own git worktree, whether or not the user mentions one. The main checkout is the user's.

1. **Start**: call `EnterWorktree` with a short kebab-case name for the task before the first edit. It branches `worktree-<name>` from `origin/dev` (`worktree.baseRef: "fresh"`) under `.claude/worktrees/`. The `prepare-worktree` hook runs `pnpm install`; `apps/web/.env.local` isn't copied (step 3 writes the worktree's own). If `node_modules` is still missing, run `pnpm install --frozen-lockfile`.
2. **Branch**: rename the branch to the repo's `<type>/<topic>` form (`git branch -m feat/billing`) before you push. For a recurring topic, put the issue numbers in it (`chore/friction-139-151`): GitHub deletes a merged PR's branch on `origin`, but the local copy stays, so a reused name fails with "a branch named … already exists".
3. **Run**: `pnpm dev` serves the worktree at `https://<branch>.cognitive-wealth.localhost`, never on the main checkout's dev data: it first gives the worktree its own database and Redis prefix on the verification services (`compose.verify.yaml`; Mailpit there is shared), and writes its `apps/web/.env.local`, which the database CLIs read too. `pnpm dev:env` does that without starting the app. Compose and `.secrets/` stay in the main checkout and serve every worktree. How it works: `docs/dev-sign-in.md`, "In a git worktree".
4. **Sync**: to pick up a newer `dev`, run `git fetch origin && git rebase origin/dev` in the worktree and resolve conflicts there. In the main checkout, only `git pull --ff-only` (or `git merge --ff-only origin/dev`) is allowed. Run it when `dev` has moved, since the hooks run from the main checkout's copy, and install afterwards: a fast-forward brings new dependencies but doesn't install them, and the `teardown-worktree` sweep then fails with `ERR_MODULE_NOT_FOUND`. A worktree session can't run either (isolation refuses `git -C <main checkout>`), so ask the user to type `! git -C <main checkout> pull --ff-only`, then `! pnpm -C <main checkout> install --frozen-lockfile`.
5. **Finish**: commit, push and open the PR from the worktree, ready for review (never left as a draft). Remove it (`ExitWorktree` with `remove`, or `git worktree remove`) only once the PR is merged or the user says so. Once it's gone, the `teardown-worktree` hook runs `pnpm dev:prune`, which tears down the dev environment (its `pnpm dev`, database and Redis keys) and the `verifier-web` leftovers (servers, `verify_<token>_*` databases, `--ref` checkouts, the `compose.sh` project with its volumes, the shared Chrome if it held it) of every worktree git no longer lists; when that fails, it says so, and you fix the cause and rerun `pnpm dev:prune`. The same sweep runs at every session's start and end (which catches the exit prompt's removal, subagent worktrees and `rm -rf`) and on every `pnpm dev`, so nothing outlives its worktree for long.

`.claude/hooks/require-worktree.mjs` enforces this (and `teardown-worktree.mjs`, tested in `teardown-worktree.test.ts`, the sweep in step 5). It denies edits inside the main checkout, and commands there that commit, stage, switch branches or rewrite files in place. A denial is the cue to call `EnterWorktree`, not to work around it. Reads, `gh`, a fast-forward of the main checkout and Edit/Write of files outside the repo (memory, Claude Code's scratchpad) are unaffected. An in-place rewrite (`sed -i`, `perl -pi`) from the main checkout is denied whatever its target. When the user explicitly wants work done in the main checkout, they start Claude with `CLAUDE_MAIN_CHECKOUT=1`. Its tests are `.claude/hooks/require-worktree.test.ts` (workspace `@repo/agent-hooks`, run by `pnpm test`); a change to what it allows or denies adds a case there.

Changes to `.claude/hooks/` or `.claude/settings.json` alter the agent's own guardrails, and auto mode denies them as self-modification until the user approves. Ask before the first edit, and make hook edits one at a time, so a denial can't leave a half-applied change. A session runs the hooks and settings of the checkout it started in, so one started in the main checkout keeps running the main checkout's copy after `EnterWorktree`. Besides its tests, replay the events it handles to the worktree's copy, as Claude Code would send them: `echo '{"hook_event_name":"SessionStart","source":"startup"}' | CLAUDE_PROJECT_DIR=<worktree> node <worktree>/.claude/hooks/<hook>.mjs`, from a `.dev/scratch/` script. That checks the hook against the real repo, but not the `settings.json` wiring (matchers, event names). For that, start a headless session in the worktree, which loads the worktree's `settings.json` and runs its hooks with `$CLAUDE_PROJECT_DIR` set to the worktree: from a `.dev/scratch/` script that `cd`s to the worktree root, `claude -p "<a prompt that fires the event>" --model haiku --max-budget-usd 0.2 --output-format stream-json --verbose --include-hook-events --debug-file .dev/scratch/hooks.log`. Its `hook_started`/`hook_response` lines show each event that fired with the hook's output, and the debug log names each hook command and its exit status.

A task's scratch files (scripts, intermediate output, PR bodies) go in the worktree's `.dev/scratch/` (the `prepare-worktree` hook creates it), not Claude Code's scratchpad: `.dev/` is gitignored, the hook doesn't restrict it, and it goes when the worktree is removed. The main checkout's `.dev/` holds only shared state (`verifier-web`'s `verify/`, `perf/` and `worktrees/`, and `dev-env`'s `worktree-env/` records); everything per-task stays in the worktree's, including `auth/` from `dev:sign-in`, since a session only works on the server (and database) it signed in to.

Claude Code's own worktree isolation (separate from that hook) refuses commands it can't parse for git use, with "names git in a form too complex to verify" or "too complex to verify that it stays inside the worktree", even when they never run git: `for`/`while` loops, heredocs (`cat >> file <<'EOF'`, and `python3 - <<'EOF'` too: one may pass and the next, in the same worktree, be refused, #214), multi-line quoted arguments (`gh pr create --body "…"`), a chain (`;`, `&&`) with any `git` in it, even a read-only `git diff --stat`, anything containing a URL like `github.com/…` (it matches `git` inside `github`), and a Go template argument (`docker … --format '{{.Name}}'`, `gh … --template '{{…}}'`). It also refuses a shell variable or command substitution where an argument goes (`cat $D/file`, `-F id=$(gh api …)`, "a value computed at runtime"), a relative `cd` chained with another command (`cd ../.. && …`, "a location computed at runtime"), any command with an `eval` argument (`agent-browser eval "…"`, "runs a string through eval"), writing a script and running it in the same command, and a script handed a command that points into another checkout (`sh .dev/scratch/time.sh pnpm -C <dir> test`, or `--dir <dir>`): write that command inside the script instead. The Bash tool also keeps the working directory between calls, so a `cd` leaks into later commands. In a worktree, run every command from the worktree root and reach into a package with `pnpm --filter <pkg>`, `uv run --project <dir>` or a spelled-out path rather than `cd`, edit files with Edit/Write, spell paths out instead of using variables, pass long text, or any text that mentions git, through a file in `.dev/scratch/` (`--body-file`), and put loops, heredocs, `eval` and URL-bearing commands in a `.dev/scratch/` script written with Write, then run `sh <file>` as the whole command: chained with anything else (`… ; sh <file>`), it's refused as "runs sh inside a construct too complex to verify". Files in the shared git dir (the main checkout's `.git/`, e.g. `.git/info/`) have no worktree copy and can't be written from a worktree session; ask the user to change them.

## Commands

Run from the repo root (tasks fan out via Turborepo):

- `pnpm dev`: all apps through [portless](https://portless.sh) (`web` at `https://cognitive-wealth.localhost`; a linked git worktree gets `https://<branch>.cognitive-wealth.localhost`), so no app binds a fixed port. Each app's `dev` script is `portless` and the real command is `dev:app`, named in the package's `"portless"` key; add new apps the same way. `PORTLESS=0 pnpm dev` bypasses the proxy (Next's default :3000). The first run starts the proxy on 443 (sudo prompt, local CA); in a non-interactive shell run `portless proxy start` (or `portless service install`) once first. E2E doesn't use portless: it gives each worker its own free port
- `pnpm dev:env` / `pnpm dev:teardown [--worktree <path>]` / `pnpm dev:prune [--dry-run]` (`packages/dev-env`): a linked worktree's own dev environment (database `wt_<token>`, Redis prefix `cw:wt:<token>:`, on the verification services), set up by `pnpm dev`; tear one down by hand (idempotent; to start a worktree over); tear down every one whose worktree is gone (what the `teardown-worktree` hook and `pnpm dev` run). `dev:env` and `dev:teardown` are a no-op or refusal in the main checkout
- `pnpm test`: unit and UI tests only (each package's `vitest run --project unit --project ui`). `pnpm test:integration` runs the `*.integration.test.*` files on a real Postgres in Testcontainers (needs Docker), where most auth and security rules are tested; a change that touches those packages runs both. It runs turbo under `packages/testing/src/cli/with-postgres.ts`, which starts one Postgres for every package's tasks (the custodian's pytest starts its own) ([ADR 0018](docs/adr/0018-integration-tests-on-real-postgres.md))
- `pnpm e2e`: builds `web`, then runs Playwright with Postgres, Redis and Mailpit containers and one standalone server per worker; needs Docker (`--filter=web-e2e --only` skips the build)
- Before a PR: `pnpm lint` (Oxlint, then each package's `lint`), `pnpm format:check` (`pnpm format` fixes it) and `pnpm check-types` (the turbo task is `check-types`, not `typecheck`), besides the tests above
- A suite on the base ref, say to time it before and after a change on the same machine: from a `.dev/scratch/` script (the commands name git and another checkout), `git worktree add --detach .dev/scratch/base origin/dev`, `pnpm -C .dev/scratch/base install --frozen-lockfile --prefer-offline`, then the suite there with `--force` so Turbo's cache doesn't answer (`pnpm -C .dev/scratch/base test:integration --force`), and `git worktree remove --force .dev/scratch/base` when done. Integration tests start their own Postgres there, so isolation holds
- `docker compose up --build`: Postgres 18 + migrations + Redis + Mailpit (UI on `http://127.0.0.1:8025`) + `web`, and the custodian (`http://127.0.0.1:8000`) after its own migrations on its own Postgres, `custodian-db` (`apps/custodian/README.md`). Create `.secrets/` first with the loop in `compose.yaml`'s header, which names every secret and skips the ones that exist. That's the dev stack's project (`cognitive-wealth`), so to verify a change to the images or to compose.yaml's own services, run `.claude/skills/verifier-web/compose.sh up [<service> ...]` instead: a project of the checkout's own, with its own ports, volumes and (in a worktree) throwaway secrets, its database seeded like the verify servers' so the dev users sign in, removed with `compose.sh down` or the worktree's teardown. For `pnpm dev`, run `docker compose -f compose.yaml -f compose.dev.yaml up -d db migrate redis mailpit` (Postgres on `127.0.0.1:5432`, Redis on `:6379`, SMTP on `:1025`) and `cp apps/web/.env.example apps/web/.env.local`
- `pnpm --filter @repo/db db:generate`: drizzle-kit migration from `src/schema/`; `db:migrate` applies them (`DATABASE_URL`, optional `DATABASE_PASSWORD_FILE`)
- `pnpm db:studio` (`packages/db/src/cli/studio.ts`): Drizzle Studio at `https://local.drizzle.studio`, on `DATABASE_URL` (by default `apps/web/.env.local`'s, the `pnpm dev` database), with the password file's contents put into the URL, since drizzle-kit takes only a URL. On a local database (the seed's check, `assertSeedTarget`) it signs in as `migrator`, the tables' owner, reading `db_migrator_password` beside `app`'s password file, so it can edit and delete any row without a Firm set (`app` can't, #190 and ADR 0020); anywhere else it keeps the URL's role (`src/cli/studio-connection.ts`). Chrome may block the page from reaching it until you allow "Apps on device" in the site's settings. In a worktree it opens the worktree's own database (run `pnpm dev:env` first if `pnpm dev` hasn't run there)

## Architecture

The platform overview, with diagrams of the system, packages, request flow, data model and decisions, is [docs/architecture.md](docs/architecture.md). A change that alters something a diagram shows updates its `.mmd` and re-renders it in the same commit; a new ADR adds its row and its `decisions.mmd` node there too (`docs/agents/domain.md`).

- `apps/custodian`: the simulated custodian, a Python FastAPI app run with uv ([ADR 0011](docs/adr/0011-custodian-simulator-in-python.md)). Its rules and a Python-for-TypeScript cheat sheet are in `apps/custodian/CLAUDE.md`.
- `packages/custodian-client` (`@repo/custodian-client`): Cognitive Wealth's only way to the custodian, imported as source by server code. Orval generates `src/generated/` from `apps/custodian/openapi.json` (`pnpm --filter @repo/custodian-client generate`): a `fetch` client whose requests go to `CUSTODIAN_URL` (required, no default) and whose responses are Zod-parsed, and a strict Zod schema per component, the Custodian feed's rows and Manifest included. The wire stays snake_case: each schema checks the snake_case keys and renames them to camelCase, so `PositionRow` (`zod.input`) is what arrives and `PositionRowOutput` (`zod.output`) is what our code uses. The generated files are excluded from Oxlint and Oxfmt and never hand-edited; `generated.test.ts` fails when they drift from `openapi.json`.
- `packages/design-system` (`@repo/design-system`): shadcn/ui (preset `bjbigatl2`: `base-luma` on Base UI, Hugeicons, Inter + Noto Sans headings) incl. the AI chat primitives (MessageScroller, Message, Bubble, Trace, Attachment, Marker, CodeBlock, Questionnaire). **Not built**: consumers import source (`@repo/design-system/components/button`, `/globals.css`, `/lib/utils`, `/hooks/*`) and Next transpiles it via `transpilePackages`. Run shadcn commands from `apps/web` (e.g. `pnpm dlx shadcn@latest add <name>`); its `components.json` routes components, hooks and lib into the package. Generated `components/` and `hooks/` are excluded from Oxlint; don't hand-edit them unless intended. An intended edit carries a comment saying what changed and why (e.g. `button.tsx`'s `aria-disabled:` styles), and updating a component goes through `add <name> --dry-run` / `--diff` and a merge, never `--overwrite`, which drops local edits.
- `packages/db` (`@repo/db`): Drizzle ORM over `postgres` (postgres.js), imported as source. Its conventions (import extensions, schema rules, database roles) are in `packages/db/CLAUDE.md`.
- `packages/households` (`@repo/households`): Households, People, Accounts and Account roles, framework-agnostic and imported as source ([ADR 0012](docs/adr/0012-domain-code-in-one-package-per-area.md)). Functions take the Firm's internal id as a parameter, never a session, and return DTOs with `publicId`s only. `./world` validates the world file (`world/schema.json` through Zod's `fromJSONSchema`, plus the cross-field rules `world.py` checks), `./seed` loads its CRM half, `getHouseholdOverview(db, { firmId, publicId })` gives the Household overview page its People (each with their Named-on Accounts, never counted), owned Accounts (last four digits only) and their Positions on the latest As-of date, and the `db:seed` CLI lives here because `@repo/db` can't depend on it.
- `packages/portfolio` (`@repo/portfolio`): the Firm's holdings as the Custodian reports them, framework-agnostic and imported as source (ADR 0012). For now Ingestion: `ingestDelivery(db, { firmId, asOf, source })` loads one Delivery of the Custodian feed through a `FeedSource` (`get`, `list`; `localFeedSource(dir)` now, SeaweedFS in #54) and returns `ingested`, `already_ingested` or `refused` with a `reason`. The `custodian:ingest` CLI lives here.
- `packages/auth` (`@repo/auth`): Better Auth server, imported as source and framework-agnostic (takes `Headers`, returns DTOs or typed `Result`s). Node can't load it directly (it imports `.tsx` templates).
- `packages/email` (`@repo/email`): React Email templates (`src/templates/`), `render*Email()` returning `{ subject, html, text }` (the plain text is a contract the sign-in harness parses), and `Mailer`s: SMTP (Mailpit in dev/e2e) or Resend, picked by `mailerFromEnv()`. `/testing` exports a memory mailer.
- `apps/web/Dockerfile` and `apps/custodian/Dockerfile`: all images are pinned `tag@digest`; Dependabot (`.github/dependabot.yml`) bumps them, and the custodian's `uv.lock`. So do the images tests start: from `compose.yaml` (`composeImage`), and Testcontainers' reaper (Ryuk) from `docker/testcontainers/Dockerfile`, a never-built file whose `FROM` line both harnesses read (`reaperImage()` in `@repo/testing/reaper`, `reaper_image()` in the custodian's `tests/integration/reaper.py`). Never write an image into code: put it where Dependabot looks, and read it from there. Check a reaper bump with `pnpm test:integration` and `pnpm e2e` before merging.
- `packages/testing` (`@repo/testing`): shared test tooling, imported as source. `/vitest` exports `defineVitestConfig()`, which every package's `vitest.config.ts` calls. `/react` re-exports React Testing Library plus `userEvent` and `setup()`, and registers jest-dom matchers and cleanup. `/postgres` provides the integration tests' Postgres: `createPostgresTest()` with `postgresGlobalSetup({ migrate })`, on the root run's shared server or one of its own (and `startPostgres`, shared with e2e); `/compose` reads `compose.yaml`'s pinned images. `/mailpit` and `/sign-in` are the sign-in harness behind `pnpm dev:sign-in` and the e2e `signIn` fixture.
- `packages/lint-rules` (`@repo/lint-rules`): the repo's own Oxlint JS plugin, `repo`, which `.oxlintrc.json`'s `jsPlugins` loads straight from `src/index.ts` (Node strips the types, so no build). Rules are tested with `RuleTester` from `oxlint/plugins-dev`; `oxlint/plugins-dev` exports no `Rule` or AST types, so they're derived from `RuleTester.run`.
- `packages/dev-env` (`@repo/dev-env`): a linked worktree's own dev environment. `web`'s `dev:app` is its `src/cli/dev.ts`, which in a worktree sets the environment up, runs `next dev` detached and records it in the main checkout's `.dev/worktree-env/`; in the main checkout it only runs `next dev`. Names come from the worktree id (`names.ts`), never the branch. Redis keys are deleted through the ACL's `janitor` user (`@repo/testing/redis-janitor`, shared with e2e), which `compose.verify.yaml` adds with `redis_password`.
- `packages/typescript-config` (`@repo/typescript-config`): TypeScript 7 requires an explicit `rootDir` whenever `outDir` is set. `erasableSyntaxOnly` is on everywhere, because the CLIs run under Node's type stripping, which can't run enums, namespaces or parameter properties (`constructor(readonly x: T)`); `tsc` rejects them so a CLI doesn't crash on start.

## Auth

Decisions and their reasons are in `docs/adr/` (0001 to 0008, and 0020 for Firm isolation); how the system works today is in [docs/auth.md](docs/auth.md). Change the code and `docs/auth.md` in the same commit; reversing a decision means a new ADR that supersedes the old one.

- Internal IDs never reach the browser ([ADR 0003](docs/adr/0003-internal-bigint-ids-public-uuids.md)). Server Components and Server Actions take `publicId`s and return DTOs (`PublicUser`, `PublicOrganization`, …); `viewer.internal` stays on the server.
- The browser talks to Better Auth only through the allowlist in `createAuthRouteHandler`; everything else 404s. A new browser-facing endpoint changes [ADR 0004](docs/adr/0004-browser-reaches-better-auth-through-an-allowlist.md).
- On the server, authorize with `getViewer`/`requireTenant` from `@repo/auth` (adapted in `apps/web/lib/auth/`) and scope every query to the tenant they return ([ADR 0002](docs/adr/0002-tenant-is-the-sessions-active-organization.md)). Firm-scoped domain tables also have row-level security, set per transaction by `withFirm` ([ADR 0020](docs/adr/0020-firm-isolation-by-row-level-security.md)); it doesn't cover Better Auth's tables or `audit_event`, where a missed filter still leaks, and it can't catch a wrong Firm handed in, so the Firm comes only from the session (or a CLI's `--firm`). It's no defence against SQL injection either (SQL running as `app` can set the Firm itself): keep every query parameterized, never `sql.raw` or `unsafe` on a request path. `proxy.ts` only does an optimistic cookie check.
- Revoke sessions and delete or deactivate users through Better Auth (or `revokeUserSessions`), never raw SQL: sessions are cached in Redis, so SQL alone leaves people signed in for up to 7 days ([ADR 0005](docs/adr/0005-sessions-cached-in-redis.md), [docs/incident-response.md](docs/incident-response.md)).
- Dev and test sign-in run the real email flow through the harness ([docs/dev-sign-in.md](docs/dev-sign-in.md)); the app has no backdoor, test-only route or bypass flag ([ADR 0007](docs/adr/0007-no-auth-backdoor.md)).
- Sign-in emails are sent after the response, through Next's `after()` (`apps/web/lib/auth/server.ts`), so timing can't reveal who is a client. Hosting must support `after()` ([ADR 0006](docs/adr/0006-sign-in-email-sent-after-the-response.md)), or sign-in emails silently never send.

## Code conventions

- **Named arguments.** A function with two or more parameters, besides a leading `db` (or `tx`) or, in `@repo/auth`, `auth` (the `Auth` that holds `db` there), takes them as one destructured object, so every call names what it passes: `write(db, { firmId, asOf, rows })`, `removeMember(auth, { headers, organizationPublicId, memberPublicId })`, `deliveryKey({ asOf, name })`, not `write(db, firmId, asOf, rows)`. This covers constructors and test helpers too. Callbacks whose arity an API dictates (`(row, index)`, Playwright fixtures, Better Auth's storage) are exempt: where the rule flags one, add `// oxlint-disable-next-line max-params -- <whose signature it is>`. Oxlint's `max-params` (`max: 2`) enforces it everywhere except `.claude/`, whose hooks and skill scripts change only with the user's approval. The rule can't see a two-parameter function without `db` or `auth` (`textOf(source, key)`, `nextEmail(mailbox, …)`), so review catches those. That object's type stays inline up to 3 members; with more, it moves to a named type `<Function>Args` declared just above the function (`type WriteArgs = { … }`, then `write(db, { … }: WriteArgs)`), written as a `type` alias, not an `interface`. A React component's props type is `<Component>Props` instead (`type ConfirmActionDialogProps = { … }`). The same goes for a single object parameter, even one that isn't destructured (`toPublicMember(row: ToPublicMemberArgs)`). `repo/max-inline-param-type-members` from `@repo/lint-rules` (`packages/lint-rules`, the repo's own Oxlint plugin) enforces it, everywhere `max-params` does.

Each behaviour has one owning layer: test it there, and give other layers at most one representative case.

| --------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| Unit                                          | Pure logic with many edge cases: callback-path sanitizer, allowlist path matcher, Sec-Fetch and origin rules, env parsing, device-cookie parsing, DTO mappers                                                             | Anything needing Better Auth or a database                             |
| Integration (real Postgres + Better Auth)     | The main home for auth and security rules: replay and expiry, sibling cleanup, eligibility gate, throttle rules, roles and permissions, tenant scoping (incl. `tenant_changed`), fresh-session gating, audit rows, timing | Browser behaviour                                                      |
| UI (RTL + happy-dom)                          | Component state machines: sign-in steps, resend cooldown, the confirm page not calling verify before a click, dialog confirms, focus after a row goes, refresh on stale-page errors                                       | The full journey, or server rules                                      |
| E2E (real Chromium, Redis, Mailpit, Postgres) | Only what needs the real stack (cookie flags, security headers and CSP, the scanner simulation, axe, keyboard journeys, aria snapshots); one representative case per category already covered by integration tests        | The full permission matrix, every error variant, every rate-limit rule |

Vitest 5 with three projects per package, picked by filename:

- `*.test.ts`: unit tests in Node
- `*.test.tsx`: UI tests in happy-dom. Import from `@repo/testing/react`, query by role or label, and drive interactions with `user-event` (`const { user } = setup(<X />)`), not `fireEvent`.
- `*.integration.test.{ts,tsx}`: integration tests against a real Postgres (compose.yaml's image, with `01-roles.sh`'s roles). Import `test` from `@repo/db/testing` and take `orm` (Drizzle over postgres.js, signed in as `app` with a password, as the app is), `migratorOrm` (as `migrator`, for DDL and the `drizzle` schema) or `connect(role)` (another pool, for tests that need several connections); in `@repo/auth`, `authTest` adds `t`, which waits for sign-in background work before the test's connections close. Add `// @vitest-environment happy-dom` to a file that also renders. Parameterise a test that takes fixtures with `test.for(rows)(name, (row, { orm }) => …)`, not `test.each`, which spreads the row into the arguments and passes no fixtures. A fixture from `test.extend` is set up only for a test that names it, so a test that relies on its side effect (a seeded row) destructures it even when unused (`{ invitation: _pending }`); otherwise the seeding never runs and a "nothing happened" assertion passes vacuously (#215).
- The server comes from the package's global setup: its `vitest.config.ts` calls `defineVitestConfig({ integrationGlobalSetup: "./src/postgres-setup.ts" })`, a file that re-exports `@repo/db/postgres-setup`; a new package with integration tests adds both. The setup migrates a template of the package's own (`test_template_<package>`), on the server the root run shares (`TEST_POSTGRES_SERVER`) or, for `pnpm --filter <pkg> test:integration`, one it starts itself; each test copies it into `test_db_<package>_…`, and the run fails if one of those isn't dropped. PGlite is gone ([ADR 0018](docs/adr/0018-integration-tests-on-real-postgres.md): real Postgres measured faster).
- E2E: `apps/web-e2e/tests/*.spec.ts`

Run one test file with `pnpm --filter <pkg> exec vitest run --project <unit|ui|integration> <file> [-t "<name>"]` (an integration file there starts its own Postgres). Vitest sees an agent and switches to its `minimal` reporter, which hides passing tests' `console.log`: add `--silent=false` to see it. On a failure, pnpm's `ERR_PNPM_RECURSIVE_EXEC_FIRST_FAIL` box prints last, so read the `FAIL` lines above it rather than only the tail (#181, #200).

Vitest globals are on (`globals: true` in `defineVitestConfig()`, `vitest/globals` in each package's tsconfig `types`): use `describe`/`it`/`expect`/`vi` without importing them. Library code in `@repo/testing` still imports from `vitest`.

**Test isolation is a hard requirement at every level.** No test may depend on another test's state or on execution order. No test or verification run touches the dev or production database, Redis or Mailpit: integration tests use a Testcontainers Postgres with a database per test (the TypeScript packages share one server per root run, the custodian's Python tests start their own), e2e uses Testcontainers, and runtime verification uses the in-memory `compose.verify.yaml` project with a fresh database per server (`verifier-web` skill).

- Unit/UI: mocks, env and globals are restored after each test in the shared config, and RTL cleans up the DOM.
- Integration: each package migrates its own template once per run, and each test gets its own `create database … template` copy, dropped afterwards. Never share a `db` across tests or write to module-level state.
- E2E: each worker gets its own database copy and server, and each test seeds its own data, never shared setup. The fixtures and seeding rules are in `apps/web-e2e/CLAUDE.md`.

## Accessibility

The bar is WCAG 2.2 AA, enforced at three levels:

- **Lint:** all Oxlint `jsx-a11y` rules are errors, except `control-has-associated-label`, which can't see labels passed through Base UI's `render` prop (axe covers it at runtime). `settings.jsx-a11y.components` maps `Button`/`Input`/`Label`/`Textarea` to native elements; extend that map when adding thin wrappers.
- **Component tests:** every design-system component test includes `await expect(container).toHaveNoA11yViolations()` (axe-core via `@repo/testing/react`). Colour contrast and landmarks are skipped (happy-dom has no layout). With a popup open (menu, select, popover), scan the popup element, not `document.body`: without layout axe can't tell the popup is modal and flags Base UI's `aria-hidden` focus guards (`aria-hidden-focus`), which a real browser doesn't.
- **E2E:** `tests/a11y.spec.ts` runs an axe scan of every route in `PUBLIC_ROUTES` and `SIGNED_IN_ROUTES` (`support/routes.ts`) in light and dark themes, and fails on any violation. Add new routes there; `security-headers.spec.ts` covers the same list. Use `makeAxeBuilder` from `fixtures.ts` to scan interactive states (open dialogs, menus), cover keyboard journeys (focus moves in, Escape closes, focus returns) in `keyboard.spec.ts`, and keep `aria-snapshot.spec.ts` in sync (`--update-snapshots`, then review the YAML diff).
