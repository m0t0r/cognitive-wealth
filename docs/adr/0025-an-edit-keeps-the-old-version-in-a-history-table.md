# ADR 0025: An edit keeps the old version in a history table

- Status: accepted
- Date: 2026-10-26

Cognitive Wealth plays an SEC-registered investment adviser, which must keep electronic records "so as to reasonably safeguard them from loss, alteration, or destruction" (Rule 204-2(g)(3)(i), [17 CFR 275.204-2](https://www.ecfr.gov/current/title-17/section/275.204-2)). [ADR 0021](0021-firm-and-delivery-records-cant-be-deleted.md) covers destruction; alteration is still open. An update overwrites a row, and `updated_at` says that it changed, not what it said before or who changed it. Today that happens in one place: Ingestion brings `custodial_account.registration_type` and `opened_on`, and `security.name` and `kind`, up to date with each Delivery (#126). The CRM tables are insert-only for `app` (#190), but #192's end dates and phase 4's edits will update them. The model is the audit-trail option of the broker-dealer rule, Rule 17a-4(f)(2)(i)(A) ([17 CFR 240.17a-4](https://www.ecfr.gov/current/title-17/section/240.17a-4)): every modification and deletion keeps its date and time, the identity of the individual where applicable, and enough to re-create the original. It isn't our obligation, but it's what #189 copies (#193).

1. **One history table per table `app` may update or delete.** `<table>_history` holds a full copy of the old row, as typed columns that mirror the table (not a JSON diff), plus `operation` (`update` or `delete`), `valid_until` (when the change happened) and who made it (point 3). It's Firm-scoped with `firmIsolation()`, like the table it records, and its `firm_id` restricts deletes like every other one (ADR 0021). An insert writes nothing: the current row is the first version, and the chain back from it through the history re-creates every earlier one.
2. **A trigger writes it, and `app` can't.** An `after update or delete` trigger, owned by `migrator`, `security definer` with `search_path = ''`, writes the history row in the same transaction as the change. `app` gets `select` on history tables and nothing else, so it can neither skip a version nor edit or delete one. An update that changes nothing but `updated_at` writes no row.
3. **Who changed it is one of three, checked.** `changed_by_user_id` (references `user`, `on delete restrict`), `changed_by_delivery_id` (references `custodian_delivery`) or `changed_by_system` (text, such as `seed`), with a check that exactly one is set. A User who changed a record can't be hard-deleted, which is what #110 asks for anyway; no history row names a User yet. An Ingestion change names its Delivery, so the As-of date it came with is one join away.
4. **The actor is set inside the transaction.** `setActor(tx, actor)` (`@repo/db`) sets it for the transaction only, as `withFirm` sets the Firm, before the first write. It's separate from `withFirm` because Ingestion's actor is a Delivery that only exists once the transaction has inserted it, and reads need no actor. When a history trigger fires with no actor set, it raises `Actor not set` for `app`, like `Firm not set`, so a forgotten actor fails loudly instead of leaving a version with no author. For any other role it records that role's name as `changed_by_system`, so `migrator`'s edits in `pnpm db:studio` and data migrations still work and still leave a trace.
5. **A rule, not a list.** A test reads `APP_PRIVILEGES` and fails when a domain table that grants `app` `update` or `delete` has no history trigger, so #192 and phase 4 can't add an update without its history. Exempt, with the reason in the test: `world_seed`, the seed's note of the world file it loaded, which is bookkeeping, not a record; and Better Auth's tables, whose sessions and sign-in codes churn by design, and whose membership and organization changes already go to `audit_event`.
6. **Record time now, valid time later.** History tables answer "what did our records say then?", which is the Record time the rule asks to safeguard. They don't directly answer "what was true in the world on an As-of date?", the Valid time a past fee or report needs ([docs/research/wealth-domain.md](../research/wealth-domain.md) §3.3). Versioned rows on both timelines would answer both, but every query that reads `custodial_account` or `security` would change, and nothing reads a past Registration type yet. While Restatements are refused, Deliveries arrive in As-of order, so point 3's Delivery gives each version its Valid time. Phase 2, which accepts Restatements and so out-of-order Deliveries, decides whether that still holds or versioned rows replace it.

## Consequences

- #126 is closed by this: an Account's or Security's earlier details are kept, with the Delivery that replaced them.
- Nothing reads history yet. The first reader, such as an Account's Registration type on a past As-of date, comes with the phase 3 fee work that needs it.
- Every write path to a table with history calls `setActor`; a domain function that updates one takes its actor from the session, the Delivery it writes, or its CLI.
- History tables are records: they go in `RECORD_TABLES` (`packages/db/src/records.ts`), so a Records export includes them, and the Users they name are among the Firm's Users.
- 17a-4's audit trail also covers creation, its time and, if applicable, who created the record. A row's `created_at` gives the time; who created it isn't kept. Today every insert is the seed's or Ingestion's, which say so through `world_seed` and `custodian_delivery`. Phase 4, when people add records, decides whether rows record their author.
- A data migration that changes rows of a table with history writes history rows attributed to `migrator`.
