# ADR 0019: The world's market data is pinned or committed, never fetched live

- Status: accepted
- Date: 2026-10-26

The simulated Custodian prices its fictional Securities from real market history ([docs/product.md](../product.md), "Fictional Securities, real market history"): Kenneth French's daily three-factor file (Mkt-RF, SMB, HML, RF) and the US Treasury's daily par yield curve. The same seed, Pin and date must always give the same day ([the prices primer](../learn/04-prices-dividends-and-the-cash-sweep.md), Part 7), so neither input may change under the world without a deliberate rebuild. #45 decided how.

1. **The Factor file is pinned to an archived copy.** `apps/custodian/market/factor-file.pin.json` holds the address the custodian downloads from, the Wayback Machine's raw-bytes form of one capture (`web.archive.org/web/<timestamp>id_/<original address>`); the library's own address, for reference only and never fetched; the zip's SHA-256; the CRSP month the file says it was built from; and its last date. The first Pin is the 2026-10-17 capture: built from the 202608 CRSP database, ending on 2026-08-31.
2. **One cache per machine, named by hash.** `factor_file()` returns the verified file from `~/.cache/cognitive-wealth/factor-files/<sha256>.zip` (`FACTOR_FILE_CACHE` overrides it). On a miss it downloads into a temporary file beside it, checks the hash, and only then renames it into place. A cached copy is hashed again on every start. A wrong hash, a failed download, or no network with an empty cache raises an error that says which, with both hashes for a mismatch. The API's start-up and `world:load` both get the file through it, so neither runs without it.
3. **Treasury yields are committed, not pinned.** `apps/custodian/market/treasury-yields.csv` holds every published tenor for every day the Treasury published from 2020-01-01 to the Factor file's last date (its days aren't quite the Business days, [the Close primer](../learn/06-the-close.md), Part 6), in percent as published. A tenor not yet published on a date (the 4-month bill before 19 October 2022, the 1.5-month before 18 February 2025) is an empty cell, read as absent, never zero. `pnpm --filter custodian yields:write` rebuilds it from the Treasury's yearly CSVs; it's run by hand when the Pin moves, never by a test or a start. The file holds the yields and nothing that depends on when it was written, so the same yields always give the same bytes, and its SHA-256 changes only when a yield does. The source address, the retrieval date and the SHA-256 of the file that run wrote go beside it, in `treasury-yields.source.json`, which nothing hashes. Run again on unchanged yields, the script writes neither file.
4. **Readers give exact fractions.** Both readers turn the published percents into `Rate`s, fractions at full precision ([ADR 0013](0013-money-shares-prices-and-rates-are-separate-types.md)), by moving the decimal point (`Decimal.scaleb(-2)`), never through a float: the file's `0.41` is `Rate("0.0041")`.
5. **The database records which inputs built it.** The `build_record` table holds one row: the Factor file's, the Treasury yields' and the Security catalog's SHA-256, and the Factor file's CRSP month. Only the hashes are compared; the month is there so a refusal reads "the 202602 CRSP file (…) and is now the 202608 CRSP file (…)", not two hashes alone. Nothing else from the Pin is stored: the download address says where the bytes come from, not what they are, so moving it to another copy of the same bytes rebuilds nothing. The first `world:load` writes it, before any other row. After that, `world:load` and the API refuse to run when the committed inputs no longer match, and say the database must be rebuilt from empty. The API checks it when it has a database (`DATABASE_URL`); `pnpm dev`, which serves no data yet, checks only the Factor file. The Security catalog's hash joined the record with #183; a database recorded before it has an empty one, so it's refused until rebuilt.
6. **Tests and verification never reach the archive.** A made-up file in the library's format, with its own Pin, lives in `apps/custodian/fixtures/factor-file/`, stored under its SHA-256 so the folder works as a ready cache. `tests/conftest.py` points every test at it, download tests use a local HTTP server, and compose.sh's custodian runs on it, mounted read-only. The image build downloads nothing; Compose keeps the cache in the `custodian-factor-files` volume.

## Why

- **An archived copy, not the library's address.** The library rebuilds its whole history every month and replaces the file at the same address: the Wayback Machine's copies of it from 2026-03, 2026-06 and 2026-10 all differ. A Pin of the live address would stop matching within a month, and a fresh clone could never start. A capture is kept as it was taken: the 2026-10-17 one downloaded twice gave the same SHA-256, and its SHA-1 matches the archive's own record (`SBGKKTFBGUEUH5VVQ4SHQTLB42ZVXR3U`).
- **Not committed.** The file ends with "Copyright 2026 Eugene F. Fama and Kenneth R. French". The yields are a work of the US government, which has no copyright (17 U.S.C. § 105), so they can be committed, and committing them is simpler than a second download path. The current year's Treasury file changes every Business day, so it couldn't be pinned by hash anyway.
- **Named by hash, verified before the rename.** A name can only ever hold its own bytes, so one cache can serve every worktree on a machine, and an interrupted or wrong download leaves nothing behind for the next start to trust.
- **No date in the yields file.** Its SHA-256 is in every database's build record. If the file recorded when it was retrieved, rerunning `yields:write` on another day would change the hash with no yield changed, and every database would have to be rebuilt for nothing. The same rule as the feed's files ([ADR 0017](0017-custodian-feed-format.md)): the bytes depend on the data alone.
- **A build record.** Prices are stored once and never rewritten. If the Pin moved and an old database carried on, one history would mix two worlds' prices, with nothing to show where. Refusing is cheap; a rebuild regenerates everything from the inputs.
- **Real history ends on one date.** Yields stop on the Factor file's last date, so after it every input is resampled by the same kind of rule (#46, #47), never a mix of real and resampled days.

## Considered options

- **Pin the library's own address.** What `docs/product.md` first said. It breaks at the library's next monthly update.
- **Commit the Factor file.** Simplest and offline, but it's someone else's copyrighted work.
- **Pin the Treasury yields too, by downloading them.** Adds a second download path, and the Treasury's files have no permanent copies to pin; it buys nothing over committing them.
- **Download in `docker build`.** Puts the file in every image layer and needs network for every build; a volume downloads it once per machine.
- **Trust a cached file by its name.** Faster, but a file changed or truncated on disk would then be used. Hashing 180 KB on each start costs nothing noticeable.
- **Keep yields as published percents.** Fewer conversions, but every caller would have to remember the unit; ADR 0013's `Rate` is a fraction, so the readers convert once, exactly.

## Consequences

- **The pinned Factor file has one public source**, the Wayback Machine's capture. While the archive is down, a machine with nothing cached can't start the custodian; machines that have the file start as before, since a start only re-hashes the cached copy. If the capture were ever removed, for example after a takedown request, no fresh setup could start, and the same history couldn't be rebuilt: the library's later files, and other captures, have other contents.
- **Any copy with the right bytes will do.** The cache trusts a file for its SHA-256, not for where it came from, so a backup copied into the cache folder as `<sha256>.zip` is checked and used like a download. Keep a private backup of each pinned zip (never commit or publish it: it's Fama and French's copyrighted work). If the capture is gone and no copy is left, the only way on is moving the Pin to another copy, which rebuilds the world with different history.
- **#187** will check for newer Factor files and prepare a Pin move as a PR; it should also notice when the pinned capture stops being served.
